Votre portail académique sécurisé par Auth0

Consultez vos notes ou saisissez celles de vos étudiants. L'identité est vérifiée par Auth0 via Universal Login ; UniPortal reçoit des jetons signés et applique les rôles de chacun.

Fonctionnalités

Ce qu'Auth0 apporte à UniPortal

Chaque brique illustre une notion du chapitre 3 et reste visible dans la démonstration.

Universal Login

La page de connexion est hébergée par Auth0. UniPortal ne manipule jamais le mot de passe : il redirige vers le tenant et récupère un résultat vérifiable.

§3.3.3 Universal Login

Connexion sociale

Un compte Google peut servir à se connecter. Auth0 fédère le fournisseur externe et renvoie à UniPortal un profil normalisé, sans mot de passe local.

§3.3.4 Connecteurs d'identité

RBAC

Les rôles « etudiant » et « enseignant » sont définis dans Auth0 et injectés dans les jetons par une Action. L'interface s'adapte au rôle reçu.

§3.5.3 RBAC et scopes

JSON Web Tokens

Les jetons émis sont des JWT signés en RS256. L'inspecteur du tableau de bord décode leurs trois parties et rappelle qu'un jeton lisible n'est pas un jeton validé.

§3.2.5 JWT - §3.6.2 Validation

MFA adaptatif

Une preuve supplémentaire (application OTP, notification) peut être exigée selon le risque : nouvel appareil, localisation inhabituelle, compte enseignant.

§3.5.2 Authentification multifacteur

Journaux d'audit

Chaque connexion, échec ou changement de configuration est consigné dans les logs du tenant, exportables vers un SIEM pour le diagnostic et l'enquête.

§3.5.5 Journaux et audit
Flux de connexion

Authorization Code + PKCE, étape par étape

Les six étapes du §3.4, avec les requêtes HTTPS réellement échangées sur TCP/443.

Utilisateur SPA UniPortal Tenant Auth0 API métier
  1. 1
    Utilisateur → SPA

    Demande d'accès

    Aucune session valable : le SDK prépare le flux en générant un secret éphémère (PKCE), un state et un nonce.

    // Généré dans le navigateur, jamais transmis tel quel
code_verifier  = random(43..128 caractères)
code_challenge = BASE64URL(SHA256(code_verifier))
state = random()   nonce = random()
  2. 2
    SPA → Auth0

    Redirection vers /authorize

    Le navigateur résout le domaine du tenant (DNS) et ouvre l'endpoint d'autorisation. L'URI de redirection doit être strictement autorisée.

    GET /authorize?response_type=code
  &client_id=VOTRE_CLIENT_ID
  &redirect_uri=https://uniportal/callback.html
  &scope=openid profile email offline_access
  &code_challenge=E9Melhoa2Ow...
  &code_challenge_method=S256
  &state=xyz&nonce=n-0S6
Host: VOTRE-TENANT.auth0.com
  3. 3
    Navigateur ↔ Auth0

    Vérification de l'utilisateur

    Universal Login présente les méthodes activées : mot de passe, Google, puis une étape MFA si la politique l'exige.

    POST /u/login?state=hKFo2SBx...
Content-Type: application/x-www-form-urlencoded

username=etudiant@univ.fr&password=********
// Le mot de passe reste sur le domaine Auth0
  4. 4
    Auth0 → SPA → Auth0

    Retour et échange du code

    Auth0 renvoie un code à usage unique. La SPA vérifie le state, puis échange le code en prouvant qu'elle détient le code_verifier.

    HTTP/1.1 302 Found
Location: /callback.html?code=SplxlOB&state=xyz

POST /oauth/token
grant_type=authorization_code&code=SplxlOB
&code_verifier=dBjftJeZ4CVP...&client_id=...
  5. 5
    Auth0 → SPA

    Utilisation des jetons

    La SPA reçoit trois jetons aux rôles distincts. Le SDK valide l'ID token (signature, iss, aud, nonce, exp).

    HTTP/1.1 200 OK
{
  "id_token": "eyJhbGciOiJSUzI1NiIs...",
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "refresh_token": "v1.MjQ5...",
  "token_type": "Bearer", "expires_in": 86400
}
  6. 6
    SPA → API métier

    Contrôle par l'API

    L'access token accompagne chaque appel. L'API vérifie signature, émetteur, audience, expiration et rôle avant de renvoyer les notes.

    GET /api/notes/me
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

// 200 si valide et autorisé
// 401 jeton absent, expiré ou mauvaise audience
// 403 identité valide mais action interdite
Sécurité

Les garde-fous du flux

Chaque paramètre répond à une menace précise. Les retirer ouvre une faille, même avec Auth0.

PKCE

Lie l'échange du code au navigateur qui a lancé le flux grâce au couple verifier / challenge S256.

Contre : interception du code - §3.4 étape 4

Paramètre state

Valeur aléatoire envoyée à /authorize et comparée au retour : la réponse correspond bien à notre requête.

Contre : CSRF sur le callback - §3.4 étape 2

Nonce

Inscrit dans l'ID token par Auth0 et vérifié par le SDK : un jeton capturé ne peut pas être rejoué.

Contre : rejeu de jeton - §3.6.2

HTTPS / TLS

Tous les échanges passent par TLS sur TCP/443. La validation du certificat authentifie le tenant.

Contre : écoute et usurpation - §3.7.2

Rotation des refresh tokens

Chaque renouvellement émet un nouveau refresh token et invalide l'ancien. Une réutilisation révoque toute la famille.

Contre : vol de refresh token - §3.6.1

Redirect URI stricte

Auth0 ne renvoie le code qu'aux URL listées dans « Allowed Callback URLs », comparées à l'identique.

Contre : détournement du retour - §3.6.3
